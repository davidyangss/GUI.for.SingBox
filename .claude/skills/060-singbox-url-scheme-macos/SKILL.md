# GUI.for.SingBox URL Scheme Fix On macOS

Use this skill when `singbox://` hyperlinks in the browser cannot launch `GUI.for.SingBox.app` on macOS.

## Problem Description

When clicking a `singbox://` link in a browser (e.g., `singbox://install-config/?url=...`), macOS should:

1. Recognize that `singbox://` protocol belongs to `GUI.for.SingBox.app`
2. Launch or activate the app
3. Pass the URL to the app for processing

If clicking the link does nothing or shows an error, the root cause is usually one of:

- **Missing `CFBundleURLTypes` in `Info.plist`** — macOS does not know `singbox://` belongs to this app
- **Missing `Mac.OnUrlOpen` in Go code** — when the app is already running, macOS calls `OnUrlOpen` but there is no handler

## Goal

Make `singbox://` URL scheme work on macOS by:

1. Registering the scheme in `wails.json` so Wails build writes `CFBundleURLTypes` to `Info.plist`
2. Adding `Mac.OnUrlOpen` handler in `main.go` to receive URLs when app is running
3. Verifying the registration after rebuild and install

## Diagnosis Steps

### Step 1: Check current Info.plist for URL scheme registration

Run on the installed app:

```bash
cat /Applications/GUI.for.SingBox.app/Contents/Info.plist
```

Or specifically check for URL scheme:

```bash
/usr/libexec/PlistBuddy -c "Print :CFBundleURLTypes" /Applications/GUI.for.SingBox.app/Contents/Info.plist
```

**If output shows "Does not exist" or empty**, the URL scheme is not registered. This is the root cause.

**If output shows `singbox` under `CFBundleURLSchemes`**, registration is correct. The issue may be elsewhere (see troubleshooting section).

### Step 2: Check wails.json for protocols configuration

```bash
cat wails.json
```

Look for `info.protocols` section. If missing, Wails will not write `CFBundleURLTypes`.

### Step 3: Check main.go for OnUrlOpen handler

Search in `main.go`:

```go
Mac: &mac.Options{
    // ... other options
    OnUrlOpen: func(url string) { ... },
}
```

If `OnUrlOpen` is missing, URLs will not be received when the app is already running.

## Fix Implementation

### Fix 1: Add protocols to wails.json

Add the `protocols` section under `info` in `wails.json`:

```json
{
  "$schema": "https://wails.io/schemas/config.v2.json",
  "name": "GUI.for.SingBox",
  "outputfilename": "GUI.for.SingBox",
  "frontend:install": "pnpm install",
  "frontend:build": "pnpm run build",
  "frontend:dev:watcher": "pnpm run dev",
  "frontend:dev:serverUrl": "auto",
  "wailsjsdir": "frontend/src/bridge",
  "author": {
    "name": "GUI.for.Cores",
    "email": "GUI.for.Cores@github.com"
  },
  "info": {
    "copyright": "Copyright",
    "comments": "https://github.com/GUI-for-Cores",
    "protocols": [
      {
        "scheme": "singbox",
        "description": "GUI.for.SingBox Protocol",
        "role": "Viewer"
      }
    ]
  }
}
```

**What this does:**

- Wails build reads `info.protocols` during packaging
- It generates `CFBundleURLTypes` in `Info.plist` with:
  - `CFBundleURLName`: `com.wails.singbox`
  - `CFBundleURLSchemes`: `["singbox"]`
  - `CFBundleTypeRole`: `Viewer`

**Expected Info.plist output after fix:**

```xml
<key>CFBundleURLTypes</key>
<array>
    <dict>
        <key>CFBundleURLName</key>
        <string>com.wails.singbox</string>
        <key>CFBundleURLSchemes</key>
        <array>
            <string>singbox</string>
        </array>
        <key>CFBundleTypeRole</key>
        <string>Viewer</string>
    </dict>
</array>
```

### Fix 2: Add OnUrlOpen handler to main.go

Add the `OnUrlOpen` callback in the `Mac` options section:

```go
Mac: &mac.Options{
    TitleBar:             mac.TitleBarHiddenInset(),
    Appearance:           mac.DefaultAppearance,
    ContentProtection:    bridge.Config.ContentProtection,
    WebviewIsTransparent: true,
    WindowIsTranslucent:  true,
    About: &mac.AboutInfo{
        Title:   bridge.Env.AppName,
        Message: "© 2026 GUI.for.Cores",
        Icon:    icon,
    },
    OnUrlOpen: func(url string) {
        runtime.Show(app.Ctx)
        runtime.EventsEmit(app.Ctx, "onLaunchApp", []string{url})
    },
},
```

**What this does:**

- macOS calls `application:openURLs:` when a `singbox://` link is clicked while the app is running
- Wails exposes this through `Mac.OnUrlOpen`
- The callback:
  1. Shows the main window (`runtime.Show`)
  2. Emits `onLaunchApp` event with the URL to frontend

**Why both `OnUrlOpen` and `OnSecondInstanceLaunch` are needed:**

| Scenario | Handler Used | Source |
|----------|--------------|--------|
| App not running, link clicked | `OnSecondInstanceLaunch` | URL passed as command line argument |
| App running, link clicked | `OnUrlOpen` | macOS `application:openURLs:` callback |

Both handlers emit `onLaunchApp` event, so frontend code handles them uniformly.

### Fix 3: Frontend (no change needed)

The frontend handler in `frontend/src/hooks/useAppLifecycle.ts` already processes `onLaunchApp`:

```ts
const offLaunchApp = EventsOn('onLaunchApp', async ([arg]: string[]) => {
  if (!arg) return

  let _url
  let _name = sampleID()

  const url = new URL(arg)
  if (url.pathname === '//install-config/') {
    _url = url.searchParams.get('url')
    _name = url.searchParams.get('name') || sampleID()
  } else if (url.pathname.startsWith('//import-remote-profile')) {
    _url = url.searchParams.get('url')
    _name = decodeURIComponent(url.hash).slice(1) || sampleID()
  }

  if (!_url) {
    message.error('URL missing')
    return
  }

  try {
    await subscribesStore.importSubscribe(_name, _url)
    message.success('common.success')
  } catch (error) {
    message.error(error)
  }
})
```

Supported URL formats:

| URL Pattern | Action |
|-------------|--------|
| `singbox://install-config/?url=xxx&name=yyy` | Import subscription |
| `singbox://import-remote-profile?url=xxx#name` | Import remote profile |

### Step 4: Check Launch Services cache (critical after reinstall)

If `Info.plist` has correct `CFBundleURLTypes` but `open "singbox://..."` returns `kLSApplicationNotFoundErr (-10814)`, the Launch Services cache has not been updated. This almost always happens after replacing an app in `/Applications/` with a new build.


```bash

```

Expected behavior:

- App window appears (if not running, app launches; if running, window is shown)
- Subscription import dialog opens with the URL

## Troubleshooting

### Info.plist correct but `open` shows kLSApplicationNotFoundErr (-10814)

This is the most common real-world scenario: the app's `Info.plist` contains correct `CFBundleURLTypes`, but macOS still reports `kLSApplicationNotFoundErr` when you run `open "singbox://..."`.

**Root cause**: macOS Launch Services maintains a cached database of URL scheme → app bindings. When you replace an app in `/Applications/` (e.g. `cp -R` a new build over the old one), the Launch Services cache does **not** automatically pick up the new `CFBundleURLTypes`. It still has the old binding (or no binding) in memory.

**Solution 1 — Force re-register just this app (recommended, lightweight)**:

```bash
/System/Library/Frameworks/CoreServices.framework/Versions/A/Frameworks/LaunchServices.framework/Versions/A/Support/lsregister -f /Applications/GUI.for.SingBox.app
```

The `-f` flag forces `lsregister` to re-read the app's `Info.plist` and update its URL scheme binding in the database. This is fast and does not require a restart.

After running this command, test immediately:

```bash
open "singbox://import-remote-profile?url=https%3A%2F%2Fexample.com%2Fconfig%23name"
```

**Solution 2 — Rebuild entire Launch Services database (heavier, if Solution 1 fails)**:

```bash
/System/Library/Frameworks/CoreServices.framework/Versions/A/Frameworks/LaunchServices.framework/Versions/A/Support/lsregister -kill -r -domain local -domain system -domain user
```

Then **restart macOS** (or at least log out and log back in) for the rebuilt database to take full effect.

### URL scheme registered but app still does not launch

1. **Check if another app registered the same scheme**

   Multiple apps can register the same scheme, but macOS picks one unpredictably:

   ```bash
   /System/Library/Frameworks/CoreServices.framework/Versions/A/Frameworks/LaunchServices.framework/Versions/A/Support/lsregister -dump | grep -i singbox
   ```

   If another app appears, that app may be handling the link instead.

2. **Rebuild Launch Services database**

   ```bash
   /System/Library/Frameworks/CoreServices.framework/Versions/A/Frameworks/LaunchServices.framework/Versions/A/Support/lsregister -kill -r -domain local -domain system -domain user
   ```

   Then restart macOS and test again.

3. **Check app signature**

   Unsigned or ad-hoc signed apps may have issues with URL schemes:

   ```bash
   codesign -dvvv /Applications/GUI.for.SingBox.app
   ```

   If `Signature=adhoc`, re-sign with a proper certificate.

### URL passed but frontend does not process it

1. **Check frontend console for errors**

   Open DevTools in the app and look for errors when clicking a link.

2. **Verify onLaunchApp event is received**

   Add temporary logging in `useAppLifecycle.ts`:

   ```ts
   EventsOn('onLaunchApp', async (args) => {
     console.log('onLaunchApp received:', args)
     // ... rest of handler
   })
   ```

3. **Check URL format**

   The frontend expects specific path formats:
   - `//install-config/` (note the double slash after scheme)
   - `//import-remote-profile`

### OnUrlOpen not called

1. **Verify main.go change is correct**

   The `OnUrlOpen` callback must be inside `Mac: &mac.Options{}`.

2. **Check Wails version**

   `OnUrlOpen` was added in Wails v2.5.0. Earlier versions do not support it.

   ```bash
   wails version
   ```

## How macOS URL Scheme Works

### Architecture Overview

```
Browser                    macOS                    App
   |                         |                       |
   |  click singbox://       |                       |
   |------------------------>|                       |
   |                         |  lookup CFBundleURLTypes
   |                         |  find GUI.for.SingBox |
   |                         |---------------------->|
   |                         |                       |
   |                         |  if app running:      |
   |                         |    application:       |
   |                         |    openURLs:          |
   |                         |    -> OnUrlOpen       |
   |                         |                       |
   |                         |  if app not running:  |
   |                         |    launch app with    |
   |                         |    URL as CLI arg     |
   |                         |    -> OnSecondInstance|
   |                         |    Launch             |
```

### CFBundleURLTypes Role

`CFBundleURLTypes` in `Info.plist` tells macOS:

- Which URL schemes this app can handle
- What role the app plays (`Editor` = can modify, `Viewer` = can only view)
- Unique identifier to distinguish from other apps claiming the same scheme

### application:openURLs: (macOS)

When app is running and a registered URL scheme link is clicked:

1. macOS calls `-[NSApplication application:openURLs:]`
2. Wails bridges this to `Mac.OnUrlOpen` callback in Go
3. Go code can then process the URL

### SingleInstanceLock

When app is not running and URL scheme link is clicked:

1. macOS launches app with URL as a command line argument
2. If `SingleInstanceLock` is configured:
   - First instance starts normally
   - If a second instance tries to start with URL arg, `OnSecondInstanceLaunch` is called in the first instance
   - The URL is passed through `data.Args`
